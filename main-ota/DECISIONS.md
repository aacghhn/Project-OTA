# 설계 결정과 외부 정보 채택

- 프로젝트에서 확정한 예약·재고·결제·취소 정책은 공통 계약으로 유지했다. 화면 문구, 공식 안내와 외부 API는 서로 다른 근거로 분류했다.
- 원문에 실제 업무 화면이 없더라도 본문에 명시된 요구사항을 계약에 포함했다. 새 필드명·형식·필수성·null·길이·허용값은 각 속성 곁의 `가정:` 주석과 설명에서 결정 이유를 확인할 수 있다.
- 실제 입력값·placeholder·버튼 상태를 관찰한 사실과 API 설계에서 새로 선택한 값을 섞지 않았다. 세부 필드의 결정과 이유는 Java·Swagger·OpenAPI 속성 설명에 보존했다.

## 주요 가정

- 외부 식별자는 1~64자 문자열, 변경 요청의 멱등 키는 1~128자 문자열이다. 인증된 주체·작업·키와 요청 내용을 함께 대조한다.
- 인증은 Bearer 방식이며 계정 식별자는 신뢰된 `Principal`에서 받는다. 역할 불일치는 403, 존재하지 않거나 소유 범위 밖인 자원은 404로 처리한다.
- 검색·상품 비교에 필요한 객실별 인원 배열은 일부 읽기 전용 POST로 전달한다. 검색과 견적 조회는 선점하지 않는다.
- 예약 견적은 10분 유효 서명 토큰으로 전달한다. 예약 수락과 확정 시 현재 조건을 다시 검증한다. 선점 자체의 기본 10분 정책과는 별개다.
- 취소 예상 비용의 동의 토큰은 5분간 유효하다. 실행 시 비용이 바뀌면 재확인을 요구한다. 이미 취소된 예약에는 최초 결과를 반환한다.
- 공개 연락 정보는 숙소가 제공하고 서비스 운영팀이 정확성과 공개 허용 여부를 확인한다. `AVAILABLE`, `NOT_PROVIDED`, `UNVERIFIED`를 구분하며 연락 경로 조회를 FAQ 열람에 종속시키지 않는다.
- 금전 결과는 확인된 사실과 진행 중·결과 불명을 구분한다. 성공 수금 P, 성공 환불 R, 최초 고객 부담 비용 F를 각각 보존하고, 확인된 환불 필요액은 `max(P-R-F, 0)`, 미수 비용은 `max(F-(P-R), 0)`으로 표시한다. 미확인 작업이 남아 있으면 최종 확정액으로 표시하지 않는다.

- 가정: 응답 키는 항상 포함하며 업무상 부재는 명시적 null로 표현한다. 빈 배열·0·false와 부재를 구분하기 위한 결정이며, 필드별 허용 조건은 Java·Swagger·OpenAPI에 명시했다.
- 가정: 초기 공개 안내는 ko-KR이며 인증 없이 열람한다. 공개 연락 유형은 PHONE·EMAIL·WEB으로 정하고 유형에 맞는 값 하나만 제공한다. 관찰되지 않은 연락 시간은 null로 두어 임의 운영 시간을 보장하지 않는다.
- 가정: 숙소 국가는 KR, 우편번호는 5자리, 성급은 0~5, 후기 점수는 별도 0~10으로 정했다. 사진은 1~50장·대표 한 장·순서 중복 없음으로 제한한다. 화면의 속성을 관찰한 결과가 아니라 입력과 표시 계약을 구체화한 결정이다.
- 가정: 상품 구성과 판매 상태 변경은 version/expectedVersion을 비교하여 충돌 시 409를 반환한다. 동시 수정으로 다른 변경이 사라지는 것을 방지하기 위한 결정이다.
- 가정: 고객 취소와 판매 중단의 상세 사유는 선택 자유문장 1~500자, 숙박 제공 불가 사유는 필수 자유문장 1~500자다. 확인된 구조화 선택지가 없어 자유문장을 선택했고, 제공 불가에는 구체적인 상황을 남기도록 필수를 선택했다.
- 가정: 예정 청구의 중복 방지 키는 chargeId로 정하고 같은 논리 시도와 외부 요청 키를 재사용한다. 예정 청구가 없는 예약은 404를 반환하여 즉시 결제와 혼동하지 않도록 했다.

## 외부 정보에서 자체 정책으로 채택한 내용

- 숙소명·이전 이름·체인·브랜드·성급, 행정구역·우편번호·영문 및 언어별 주소를 각각 구분했다. 성급과 고객 후기 평점은 다른 정보다.
- 숙소와 객실의 설명·시설·사진을 귀속 대상별로 분리했다. 객실 내부명은 운영용으로 구분하고, 면적은 제곱미터, 침대 종류와 수량은 별도 값으로 표현했다.
- 시설은 카탈로그에서 선택한다. 자유 입력으로 새 시설명을 만드는 기능은 제공하지 않는다. 주요 시설과 전체 시설, 객실별 시설을 구분했다.
- 사진의 귀속·태그·대표 여부·순서와 연결 삭제를 채택했다. 최소 1장, 800×600픽셀 이상, 파일당 4MB 기준을 채택했으며, **4MB는 4,000,000바이트**, 형식은 JPEG/PNG, 전송은 Base64 JSON으로 구체화했다. 이것은 이번 자체 설계의 결정이다.
- 조식·점심·저녁 혜택을 별도 선택지로 채택했다. 포함 혜택의 조건은 예약 당시 약속에도 보존한다.
- 예약 번호와 선택적 별도 참조 번호, 대표 투숙객의 이름과 성을 서로 구분했다. 현재 상품 설명과 예약 당시 설명을 혼합하지 않는다.
- 공개 안내의 분류·질문·답변 탐색과 숙소 연락 방법의 직접 조회를 채택했다. 열람이나 외부 연락 경로 이용을 실제 문의 접수·메시지 전달·문제 해결 완료로 취급하지 않는다.

- 환불 요청·처리 확정·금융기관 입금을 서로 다른 사건으로 구분했다. requestedAt과 resultConfirmedAt을 따로 제공하고 실제 은행 입금을 확인된 사실처럼 표시하지 않는다. 환불별 대상 금액과 통화를 보존한다.
- 숙소·객실 유형·요금제·숙박일의 대상 구분, 하루 가격과 예약 총액의 분리, 같은 객실 유형의 모든 요금제가 판매 수량을 공유하는 의미를 채택했다. 날짜 범위는 시작 포함·종료 제외이며 통화를 명시한다. 자체 점유와 판매 여유는 서버 계산값이다.
- 객실 유형과 요금제의 활성·비활성 의미를 OPEN/SUSPENDED로 채택했다. 상위 대상이 중단되면 상품만 열어도 판매할 수 없고, 중단해도 가격·한도·확정 예약은 유지한다. 재개 전 영향은 조회로 확인하며 OPEN 설정과 실제 예약 수락 가능성을 구분한다.
- 파트너의 소유 숙소 선택 후 예약 목록·상세 조회, 확정 예약 필터, 객실·요금제·숙박일별 가격·금액·통화·취소 비용 표시를 채택했다. 예약 당시 객실 설명과 현재 추가 설명·조회 시각을 별도로 제공한다.
- 공개 연락 안내에는 예약 번호, 조건부 별도 참조 번호, 체크인·체크아웃, 대표 투숙객의 영문 이름·성을 준비할 정보로 구분한다. 공개 응답에 실제 개인 값을 넣지 않는다.
- 권한 있는 파트너가 예약을 특정하고 사유를 남겨 결과를 확인하는 흐름을 채택했다. 취소 완료와 금전 처리 완료는 별개이며 외부 보고 코드나 정수 식별자를 그대로 복제하지 않는다.

## 채택하지 않은 내용과 경계

- 외부 업체의 환불 시작 24~48시간, 은행 반영 최대 15영업일·일부 카드 45영업일, Wise·Hyperwallet·AgodaCash·PayPal 경로와 이메일 통지를 자체 보장이나 실행 기능으로 도입하지 않았다.
- 쿠폰 실제 할인, 광고 구매·과금·정산, 실제 보유 객실 수, 개별 호실 배정, PMS·CM 연동, 대체 숙소·추가 보상, 부분 취소·예약 변경, 노쇼 자동 판정·과금은 제외 범위를 유지했다.
- 외부 가용 수량을 자체 OTA 판매 한도·점유·여유와 동일시하지 않았다. 수량 254/255 규칙, 소수 가격, 가격 0의 판매 중단 의미, 외부 부분 성공 응답을 자체 계약으로 옮기지 않았다.
- 현장 수금 표시를 미래 자동 PG 청구로 바꾸지 않았다. 외부 예약 메시지의 신규·변경·취소 구분을 자체 예약 상태와 동일시하지 않았다.
- 가격 연동·자동 연장·공시가격·자동 재고 보충·재고 알림은 현재 상품 구성과 날짜별 수동 관리 범위에 포함하지 않았다. 외부 설명 자동 생성은 자체 짧은 소개·상세 소개의 명시적 입력으로 정했다.
- 외부 상담 입력·첨부·전송·피드백 버튼은 외부 화면의 탐색·상담 기능으로 구분했다. 새 상담 접수·메시지 저장·담당자 배정·답변 시스템은 만들지 않았다.

- 외부 도움말의 카드 변경 질문만으로 예정 결제 수단 변경을 허용하지 않는다. 외부 중단 사유 목록과 FULLY_BOOKED를 자체 고정 사유·판매 상태로 가져오지 않았다.
- 외부 제공 불가 취소의 자동 판매 복구 규칙은 채택하지 않았다. 전체 점유는 해제하되 판매 차단·가격·한도 설정을 보존하고 취소 자체로 판매 상태를 자동 변경하지 않는다.
- 외부 예약 수신 대기열·수신 확인·복구, 현장 수금, 유예기간 예외, 카드 문제·노쇼·고객 행위 보고와 비용 면제 선택을 추가하지 않았다. 대표 투숙객 외 개별 객실 투숙객 이름이나 계정 연락처도 임의로 추가하지 않았다.

## DTO 파일 통합과 응답 필드 경로

- 실제 요청 본문 루트 19개와 정상 응답 루트 32개의 이름을 유지하고 보조 record·기능별 enum을 사용하는 루트 내부에 배치했다. 요청 JSON 구조는 바꾸지 않았다. ErrorResponse 구조와 공통 상태 enum 네 개의 이름·코드를 유지한다. RefundStatus의 복구 판단 설명은 실제 평탄 필드명과 적용 조회에 맞춰 고쳤다.
- 가정: 응답의 단일 객체를 재귀적으로 펼칠 때 대상·시점을 접두어로 표현한다. 예약 당시 약속에는 `booked`를 사용하여 현재 상품·예약 상태와 구분한다. 금액과 통화를 서로 다른 필드로 보존하며 서로 다른 대상의 같은 이름을 합치지 않는다.
- 배열의 순서·항목값·최소/최대 개수·중복 제약을 보존했다. 배열 자체를 펼치지 않고 배열 항목의 단일 객체만 접두어 필드로 바꾼다.
- nullable 객체의 부재는 파생 필드 전체의 null로 표현한다. 존재 여부를 판단할 필수 값과 그룹이 존재할 때 필수인 값 전체를 구분한다. 그룹 부재의 null과 존재하지만 항목이 없는 배열 `[]`, 금액 0, boolean false는 같은 값으로 처리하지 않는다. nullable 배열이 없을 때 항목도 없지만 배열이 있을 때 항목의 원래 nonnull 조건은 유지한다.
- 기존 scalar nullable 사유, 상태별 표시 조건, 최초 취소 결과 보존, 결과 불명 확인과 실패 확정 후 처리 조건을 해당 설명에 남겼다. 코드 파일을 줄이기 위해 검증·타입·값·업무 조건을 축소하지 않는다.
- 미사용 MoneyResponse 파일과 참조되지 않는 이전 helper 스키마를 제거했다. HTTP path·parameter·requestBody·response 및 component 참조를 재귀적으로 확인하고 실제 Java 스키마 이름과 공통 enum을 유지했다.
- 응답 JSON 필드 경로 변경은 클라이언트 수정이 필요한 계약 변경이다. 업무 정책, 접근 조건, 멱등성·상태 전이·HTTP 상태는 그대로이며 별도 서비스 구현이나 DB·PG 연동을 추가하지 않았다.

- nullable 숙소 문자열은 null을 허용하면서 기존 Java `@NotBlank`의 공백 정의를 유지하도록 Java 17 기준 25개 공백을 명시한 portable 패턴을 사용한다. 8개 속성의 Swagger/OpenAPI에 원래 Java 제약을 명시한 변화이며 업무 정책 추가는 아니다. 국가·우편번호는 기존 허용값과 패턴을 유지한다.
- 연락 가능 시간의 가상 속성 예시는 EMAIL 유형에 맞는 매일 09:00~18:00(Asia/Seoul) 확인 조건으로 교정했다. 실제 관찰한 숙소 운영 정책을 바꾼 것이 아니며 미확인 연락 조건은 여전히 null이다.
